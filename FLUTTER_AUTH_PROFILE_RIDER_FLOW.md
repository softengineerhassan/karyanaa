# Flutter Integration Guide: Authentication, Update Profile, and Rider Profile

This document is aligned with the current backend implementation in this repository.

## 1) Base URL and Common Response Shape

Base URL (local):
- http://127.0.0.1:8069/api/v1

Most successful APIs return:
- success: boolean
- message: string
- data: object or array (optional)

Example success response:

  {
    "success": true,
    "message": "Success",
    "data": { ... }
  }

Error format can be one of these:
- FastAPI HTTPException style:
  {
    "detail": "..."
  }
- Custom AuthServiceException style:
  {
    "success": false,
    "message": "...",
    "details": { ... }
  }

## 2) Authentication Flow (Implemented)

### 2.1 Register
Endpoint:
- POST /auth/register

Request body fields:
- employee_id: string, required, max 10, must include:
  - at least one letter
  - at least one digit
  - at least one special character
- password: string, required, min 8
- full_name: string, required, min 2, max 255
- phone_number: string, optional, max 20

Notes:
- On register, backend stores a placeholder internal email.
- Response email is null intentionally until user updates profile email.

Example request:

  {
    "employee_id": "AB1#X9",
    "password": "SecurePass123!",
    "full_name": "Hassan",
    "phone_number": "03086881047"
  }

Example response data:
- user_id
- employee_id
- email: null
- full_name
- is_email_verified: false
- message

### 2.2 Login
Endpoint:
- POST /auth/login

Request body fields:
- employee_id: string, required, same format rule as register
- password: string, required
- device_id: string, optional
- fcm_token: string, optional

Example request:

  {
    "employee_id": "AB1#X9",
    "password": "SecurePass123!",
    "device_id": "android-phone-1",
    "fcm_token": "token-if-available"
  }

Response data fields:
- access_token
- refresh_token
- token_type
- expires_in
- user:
  - id
  - employee_id
  - email
  - full_name
  - phone_number
  - is_active
  - is_superuser
  - is_email_verified
  - created_at
  - last_login_at
  - profile_picture_url

### 2.3 Refresh Token
Endpoint:
- POST /auth/refresh

Request body:
- refresh_token: string

Response data:
- access_token
- token_type
- expires_in

### 2.4 Logout
Endpoint:
- POST /auth/logout

Request body:
- refresh_token: string, optional
- revoke_all: boolean, default false

### 2.5 Get Current User
Endpoint:
- GET /auth/me
Headers:
- Authorization: Bearer <access_token>

Response data contains current user profile information and stats fields.

## 3) Update Own Profile Flow (Implemented)

Primary endpoint for auth flow:
- PATCH /auth/me/profile

Headers:
- Authorization: Bearer <access_token>
- Content-Type: application/json

Request body fields (all optional):
- email: string email
- full_name: string (min 2, max 255)
- phone_number: string (max 20)
- location: string (max 255)
- bio: string (max 1000)
- date_of_birth: date (YYYY-MM-DD)

Example request:

  {
    "email": "tracksuitwaly@gmail.com",
    "full_name": "Hassan",
    "phone_number": "03086881047",
    "location": "Lahore",
    "bio": "Mobile app user",
    "date_of_birth": "2026-04-08"
  }

Backend behavior when email changes:
- email is validated
- email uniqueness is checked
- is_email_verified is reset to false
- email_verified_at is reset to null
- verification OTP is sent to the new email automatically

Also available endpoint (older users module path):
- PATCH /users/me/profile (JSON)
- PUT /users/me/profile (multipart/form-data, supports profile_picture upload)

## 4) Email Verification Flow (After Profile Email Update)

### 4.1 Verify OTP
Endpoint:
- POST /auth/verify-otp

Request body:
- email: string email
- code: string (4 to 10 chars in schema; OTP generated by service is 4 digits)

### 4.2 Resend OTP
Endpoint:
- POST /auth/resend-otp

Request body:
- email: string email

## 5) Password Flows and Gate Rules

Important implementation rule:
- User must have a real profile email (not placeholder) before using password recovery/change flows.

### 5.1 Forgot Password
Endpoint:
- POST /auth/forgot-password

Request body:
- employee_id: string (max 10)

If profile email is missing/placeholder, backend returns:
- detail: "Please update your profile and add the email address first"

### 5.2 Verify Reset OTP
Endpoint:
- POST /auth/verify-reset-otp

Request body:
- employee_id: string
- code: string, exactly 4 characters

Response data:
- reset_token

### 5.3 Reset Password
Endpoint:
- POST /auth/reset-password

Request body:
- token: string (reset_token from previous step)
- new_password: string, min 8

### 5.4 Change Password (Logged-in)
Endpoint:
- POST /auth/change-password

Headers:
- Authorization: Bearer <access_token>

Request body:
- current_password: string
- new_password: string, min 8

Rule:
- Also blocked if user has not updated profile email yet.

## 6) Rider Profile APIs (Owner Scoped)

All rider endpoints require login token and are scoped to current logged-in user.

Route prefix:
- /riders

### 6.1 Create Rider
Endpoint:
- POST /riders

Request body:
- full_name: string, required, min 1, max 255
- phone_number: string, required, min 5, max 20
- email: string email, optional
- profile_image: string URL/path, optional, max 500

Validation rules:
- phone_number must be unique per owner user
- email must be unique per owner user (if provided)

### 6.2 List Riders
Endpoint:
- GET /riders

Returns list only for current owner user.

### 6.3 Get Rider by ID
Endpoint:
- GET /riders/{rider_id}

Returns 404 if rider does not belong to current user or does not exist.

### 6.4 Update Rider
Endpoint:
- PUT /riders/{rider_id}

Request body fields (all optional):
- full_name
- phone_number
- email
- profile_image

Same uniqueness rules apply for phone/email within owner scope.

### 6.5 Delete Rider
Endpoint:
- DELETE /riders/{rider_id}

Soft delete behavior.

Rider response fields:
- id
- owner_user_id
- full_name
- phone_number
- email
- profile_image
- created_at
- updated_at

## 7) Flutter Implementation Plan

### 7.1 Token Storage
Use secure storage for:
- accessToken
- refreshToken
- employeeId (optional helper for forgot-password flow)

### 7.2 Dio Interceptor
- Attach Authorization header if access token exists.
- On 401 from protected APIs:
  - call POST /auth/refresh with refresh token
  - retry original request once with new access token
  - if refresh fails, force logout and route to login

### 7.3 Recommended Screen Flow
1. Register screen
2. Login screen
3. Profile setup/update screen (email required)
4. OTP verification screen
5. Home
6. Forgot password flow (employee_id -> OTP -> reset token -> new password)
7. Rider list / create / edit screens

### 7.4 Frontend Guard Rules
Apply these in Flutter UI:
- Block forgot-password/change-password CTA if user profile email is missing or not verified.
- After successful PATCH /auth/me/profile with changed email:
  - show message: verification code sent
  - navigate user to OTP verify screen

### 7.5 Suggested Dart Models
Build models around these server contracts:
- StandardResponse<T>
- LoginResponse
- RegisterResponse
- CurrentUserResponse
- RiderProfileResponse
- VerifyResetOtpResponse with reset_token
